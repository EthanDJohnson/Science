# Tool catalog

Tested calculators and research tools in `.claude/skills/conundrum/scripts/`. Agents use these instead of re-deriving the same calculation. At framing, the main session checks a question's needs against this list (SKILL.md step 1).

Every calculator has a `selftest()` against independent reference values. The test suite runs all of them, including calculators promoted from runs.

**QFT quantities.** `qft_production.py` exists because QFT production errors are usually the wrong quantity computed correctly. Its self-test pins each trap to a known result:
- **In-in versus in-out.** \|β_k\|² is the in-in mean number. 1/\|α_k\|² is the in-out vacuum persistence of a mode.
- **Pair number versus vacuum decay.** Schwinger's pair rate is only the n = 1 term. The vacuum-decay rate −Σ ln(1 − n_k) = 2 Im L_eff is larger for fermions and smaller for bosons. Both are computed from the same n_k, and the self-test shows they differ.
- **Particles versus pairs.** For a real field, pairs = particles/2. For a charged field, n_k counts pairs.
- **Real production versus transient polarisation.** Numbers are defined only between static in and out regions.
- **Plane waves and free packets.** Every Fourier component of a source-free wave is null, so both give zero at first order: no phase space for massive pairs, and a vanishing gravity vertex for massless ones (Gibbons 1975). A nonzero first-order yield needs timelike support: a source, a profile that is not a vacuum solution (flagged), or a second-order background.
- **Born versus exact.** Born is only O(ε²) exact; the self-test checks it against the exact mode solver at two amplitudes.
- **Precision.** The mode solver's precision floor (about 1e-28 in \|β\|²) is measured, and results near it are flagged or refused. `qft_accuracy.py` computes below that floor.
- **Companion modules** extend the same contract: spinor Born (`qft_spinor_born.py`), second order in the background (`qft_second_order.py`), back-reaction (`qft_backreaction.py`), interactions (`qft_interactions.py`), thermal in-states (`qft_thermal.py`), curved FRW (`qft_curved_frw.py`), magnetic fields (`qft_magnetic.py`), static inhomogeneous fields (`qft_inhomogeneous.py`), and all-orders null backgrounds (`qft_plane_wave.py`). An effective second-order metric fed to Part D captures only the s-channel; use `qft_second_order.py` for physical graviton-fusion rates.

## Adding a calculator

A calculator earns a place here when several agents in a run would need the same non-trivial calculation, and when that calculation is easy to get subtly wrong. One-off arithmetic doesn't qualify; agents write that in their own `calc/` scripts.

1. **At framing,** the main session proposes it to the user with the brief.
2. **During research,** a `toolsmith` agent builds it in `runs/<slug>/tools/<name>.py`, in the tool format in `schemas.md`.
3. **At the dossier checkpoint,** the main session re-runs its self-test and reviews its reference values. It then promotes the calculator into the toolkit and adds a row above, with a line on the run that built it.
